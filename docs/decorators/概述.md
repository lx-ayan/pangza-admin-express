# 装饰器概述：框架如何「识别」到你的类

本文先回答一个核心问题：**为什么写了 `@Controller` / `@Mapper` / `@TableName`，框架就能找到并生效？**  
不是魔法，是 **TypeScript 装饰器执行时机 + Reflect 元数据 + 启动时扫描 require** 三条链路拼起来的。

---

## 1. TypeScript 装饰器什么时候跑？

装饰器在 **类被求值（定义）时** 就会执行，不是等第一次请求才跑。

```ts
@Controller("/api/user")   // ← 类定义执行到这里时，Controller() 立刻被调用
class UserController {
  @GetMapping("/list")     // ← 方法装饰器在类定义阶段执行
  list() {}
}
```

等价于编译后大致变成：

```js
let UserController = class UserController { list() {} };
// 先处理方法装饰器，再处理类装饰器（具体顺序由 TS 规范决定）
GetMapping("/list")(UserController.prototype, "list", descriptor);
Controller("/api/user")(UserController);
```

所以：**只要这个文件被 `require` / `import` 加载进内存，装饰器就已经把「路由、表名、规则」写进内存了。**

本项目依赖：

- `experimentalDecorators: true`
- `emitDecoratorMetadata: true`（`@Validate` 需要 `design:paramtypes`）
- 入口最先 `import "reflect-metadata"`（提供 `Reflect.defineMetadata`）

## 2. 元数据：装饰器「记笔记」的地方

装饰器本身几乎不做业务，只往某个 **Symbol 键** 上写数据。运行时再读出来。

```ts
// 写（装饰器阶段）
Reflect.defineMetadata(Symbol.for("pangza.controller.prefix"), "/api/user", UserController);

// 读（注册路由时）
const prefix = Reflect.getMetadata(Symbol.for("pangza.controller.prefix"), UserController);
```

可以理解为：给「类 / 方法 / 属性」挂了一个隐藏的配置袋。

| 记在谁身上 | 例子 |
|------------|------|
| 类构造函数 | `@Controller` 前缀、`@TableName` 表名、路由列表 |
| 类原型 + 方法名 | `@Param` 命名参数、部分 SQL 方法元数据 |
| 属性 | `@TableField`、`@NotNull`、`@JsonFormat` |

完整 Symbol 表见文末。

## 3. 为什么 Controller 能被「识别」并挂上路由？

完整链路：

```
Application.start()
  → loadControllers()          // 扫描磁盘，require 业务文件
      → require(".../user/index.ts")
          → 执行 @GetMapping → 把路由写入类元数据 routes[]
          → 执行 @Controller → 立刻 registerController(UserController)
              → new UserController()
              → 读 prefix + routes
              → Application.GET/POST(...).mountRoute(...)
  → routes()                   // app.use(router)
  → listen
```

### 3.1 扫描：如何找到文件？

`loadControllers` 会扫描 `src/business`（或 `Application.scan(...)` 指定的根），按层优先加载：

`entity → mapper → service → controller → advice → …`，再递归其余文件。

每找到一个 `.ts/.js` 就 `require(resolved)`。  
**require 的副作用就是：触发该类上所有装饰器。**

对应源码（简化）：

```ts
// Application.loadModuleFiles
require(resolved); // 文件一加载，@Controller / @Mapper / @TableName 全执行完
```

### 3.2 `@Controller` 为什么会自动注册？

```ts
export function Controller(prefix = ""): ClassDecorator {
  return (ctor) => {
    setControllerPrefix(Ctor, prefix);
    Reflect.defineMetadata(CONTROLLER_TYPE, true, Ctor);
    // 延迟 require Application，避免循环依赖
    const { default: Application } = require("./index");
    Application.registerController(Ctor); // ← 识别并挂路由就在这里
  };
}
```

`registerController` 做的事：

1. 用 `WeakSet` 保证同一类只注册一次（扫描 require 与装饰器触发不会重复挂路由）
2. `getControllerPrefix` / `getControllerRoutes` 读元数据
3. `new Ctor()` 得到控制器实例
4. 把实例方法 `bind` 后交给 `Application.GET/POST/...`

```ts
static registerController(Ctor) {
  if (this.registeredControllers.has(Ctor)) return this;
  this.registeredControllers.add(Ctor);
  const prefix = getControllerPrefix(Ctor);
  const routes = getControllerRoutes(Ctor);
  const instance = new Ctor();
  for (const route of routes) {
    const fullPath = joinRoutePath(prefix, route.path);
    const handler = instance[route.handlerName].bind(instance);
    this.GET(fullPath, handler, route.option); // 按 method 分发
  }
}
```

**结论：** 框架不是「猜」你有哪些 Controller，而是 **文件被加载时装饰器主动报到 Application**。扫描只是为了保证业务文件被加载。

### 3.3 方法上的 `@GetMapping` / `@Flux` 如何合并？

- `@GetMapping` 调用 `addControllerRoute`，往 `routes[]` 推一条，并合并当时已有的 Auth/Log/Flux/参数元数据。
- 若 `@Flux` 后执行，会 `rewriteRouteOption` 回写已有路由项。

所以方法装饰器**无强制顺序**。

## 5. 为什么 `@Mapper(User)` 知道表名？

分两步，都发生在**类定义时**：

**第一步：实体装饰器把表名写在 User 类上**

```ts
@TableName("sys_user")
class User {
  @TableId() id!: string;
}
// → Reflect.defineMetadata(pangza.orm.tableName, "sys_user", User)
```

**第二步：Mapper 装饰器读实体元数据**

```ts
@Mapper(User)  // 传入的是「类」本身（构造函数），不是实例
class UserMapper {}
```

```ts
function resolveMapperBinding(tableOrEntity, idFieldOrOptions) {
  if (typeof tableOrEntity === "string") {
    return { tableName: tableOrEntity, options: idFieldOrOptions }; // 直接传表名
  }
  const meta = getEntityTableMeta(tableOrEntity); // 读 @TableName / @TableId
  if (!meta?.tableName) throw new Error(`实体缺少 @TableName`);
  return {
    tableName: meta.tableName,
    options: {
      idField: ...,
      entity: tableOrEntity, // 把实体类带给 BaseMapper，供填充 / 字段 @Select
    },
  };
}
```

然后 `@Mapper` 给 `UserMapper.prototype` 挂上 `selectById` / `insert` 等方法，每个方法内部：

```ts
const mapper = table(tableName, options); // 真正的 BaseMapper
return mapper.selectById(...);
```

**结论：** 传 Entity 不是「反射猜表名」，而是 **Entity 上事先用 `@TableName` 写好了，Mapper 用 `getEntityTableMeta(Entity)` 读出来。**

详细见 [ORM.md](./ORM.md)、[Service.md](./Service.md)。

## 6. 一次请求的完整路径（把装饰器串起来）

以：

```ts
@PostMapping("/create")
@AuthCheckLogin()
@Validate()
@Log({ title: "新增用户" })
create(@RequestBody() body: CreateUserDto) { return this.userService.insert(body); }
```

为例：

```
HTTP POST /api/user/create
  → Express 命中 mountRoute 注册的 handler
  → applyRouteAuth        // 读 option.auth（来自 @AuthCheckLogin）
  → applyRouteGuards      // rateLimit / repeatSubmit（若有）
  → resolveCallbackArgs   // 按 option.params 注入 @RequestBody → req.body
  → validateMethodArgs    // @Validate + CreateUserDto 上的 @NotNull 等
  → 执行 create()
      → @Resource UserService → Container.get("UserService")
      → userService.insert → 委托 UserMapper → table("sys_user").insert
      → @TableField insertFill / 全局 fill 写 create_time 等
  → ObjectMapper.writeValue(result)  // @JsonFormat / @JsonInclude
  → ResponseData.success → res.send
  → finally: scheduleOperationLog   // @Log
```

若抛错 → `handleException` → 匹配 `@ControllerAdvice` 里注册的 `@ExceptionHandler`。

## 7. 装饰器顺序（再强调）

| 类型 | 顺序要求 |
|------|----------|
| 方法装饰器 `@GetMapping` / `@Flux` / `@Auth*` / `@Log` | **无硬性要求**（互相 rewrite / 合并） |
| 参数装饰器 | 按形参下标，互不依赖顺序 |
| 类装饰器 | 实体需先有 `@TableName` 再被 `@Mapper(Entity)` 使用（文件加载顺序上 entity 扫描在 mapper 前） |

扫描分层 `entity → mapper → service → controller` 就是为了：**先让实体元数据写好，再执行 Mapper，再执行 Service/Controller。**
